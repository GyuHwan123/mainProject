# DOCUNEX AI OCR 프로젝트 설명 스크립트

아래 문장은 발표하거나 혼자 복습할 때 그대로 읽을 수 있도록 작성했습니다.

## 1. 3분 요약 스크립트

안녕하세요. 이 프로젝트는 문서를 업로드해 텍스트를 추출하고, 추출 결과를 저장하고, AI로 문서를 활용할 수 있게 하는 DOCUNEX AI OCR 웹 애플리케이션입니다.

프로젝트는 크게 네 부분으로 나뉩니다. 첫 번째는 사용자가 보는 React 프론트엔드입니다. 로그인, 문서 미리보기, OCR 텍스트, AI 채팅, 개발자 리포트 화면이 여기에 있습니다.

두 번째는 FastAPI 백엔드입니다. 백엔드는 로그인 사용자를 확인하고, 권한을 검사하며, OCR 서버와 Supabase, Ollama를 연결합니다. 브라우저가 강력한 Supabase 서비스 키를 직접 가지면 위험하기 때문에 중요한 저장 작업은 백엔드가 담당합니다.

세 번째는 PaddleOCR 서버입니다. 일반 PDF에 문자 정보가 있으면 PDF.js가 빠르게 직접 추출합니다. 스캔 PDF나 이미지는 실제 글자가 아니라 픽셀이기 때문에 PaddleOCR로 인식합니다. OCR 결과에는 텍스트뿐 아니라 confidence와 bbox도 들어 있습니다. bbox를 사용하면 오른쪽 텍스트가 왼쪽 문서의 어느 위치에 있었는지 표시할 수 있습니다.

네 번째는 Ollama에서 실행되는 Gemma2 2B 모델입니다. 추출 텍스트를 제목과 섹션으로 구조화하거나 표로 변환하고, 문서 근거를 이용해 질문에 답합니다.

원본 파일은 Supabase Storage의 documents bucket에 저장하고, 문서 이름과 추출 텍스트, bbox는 Supabase ocr_documents 테이블에 저장합니다. 그래서 사용자가 다시 로그인해도 히스토리에서 문서를 불러올 수 있습니다.

사용자 역할은 일반 사용자와 개발자로 나뉩니다. 일반 사용자는 OCR과 AI 기능을 사용합니다. 개발자는 OCR 결과에 사람이 검수한 정답 데이터를 넣을 수 있습니다. 서버는 OCR 결과와 정답을 비교해 Precision, Recall, F1, CER를 계산하고 Supabase ocr_evaluations에 저장합니다. 리포트 화면은 이 값을 다시 조회해 문서별 성능을 보여줍니다.

현재 RAG는 질문 단어와 가장 잘 맞는 문서 청크를 찾아 Gemma에 전달하는 방식입니다. 앞으로 Embedding과 벡터 DB를 연결하면 의미가 비슷한 문장까지 더 잘 찾을 수 있습니다. Fine-tuning 화면은 질문과 모범 답변을 JSONL로 만드는 단계까지 구현되어 있고, 실제 모델 학습을 위해서는 별도의 GPU 학습 서버가 필요합니다.

이 프로젝트를 공부할 때는 화면의 버튼에서 출발해 React 함수, API 주소, FastAPI route, service, DB 순서로 따라가면 됩니다. 감사합니다.

## 2. 10분 상세 설명 스크립트

### 도입

이 프로젝트의 이름은 DOCUNEX AI OCR 웹 애플리케이션입니다. 목표는 단순히 이미지에서 글자를 읽는 것에 그치지 않고, 문서를 저장하고 다시 찾아보고 AI로 활용하고 OCR 품질까지 측정하는 것입니다.

### 시스템 구조

사용자는 브라우저에서 React 화면을 봅니다. React는 버튼 클릭과 파일 선택을 받고 화면 상태를 관리합니다. React가 직접 모든 일을 하지 않고 FastAPI 백엔드에 API 요청을 보냅니다.

FastAPI는 중앙 관리자 역할입니다. JWT로 로그인 사용자를 확인하고, 일반 사용자인지 개발자인지 검사합니다. 그리고 필요한 경우 OCR 서버, Supabase, Ollama를 호출합니다.

OCR은 계산량이 크고 별도 라이브러리가 많기 때문에 백엔드와 분리된 8001번 서버에서 실행합니다. AI 모델도 Ollama라는 별도 프로그램에서 11434번 포트로 실행합니다.

### 로그인

이메일 로그인에서는 서버가 DB에서 사용자를 찾고 해시된 비밀번호를 확인합니다. 성공하면 JWT를 발급합니다. 브라우저는 JWT와 사용자 이름, 이메일, 역할을 localStorage에 저장합니다. 이후 Axios가 API를 호출할 때 JWT를 자동으로 Authorization 헤더에 넣습니다.

로그아웃하면 Supabase OAuth 세션과 앱의 localStorage 토큰을 모두 제거하고 로그인 페이지로 이동합니다.

### OCR

파일 선택과 OCR 실행은 분리되어 있습니다. 파일을 선택하면 먼저 미리보기만 준비합니다. 사용자가 OCR 텍스트 추출 버튼을 눌러야 분석과 DB 저장이 시작됩니다.

일반 PDF는 PDF.js의 문자 레이어를 사용합니다. 이 방식은 OCR 모델이 글자를 추측하는 것이 아니라 PDF 안에 저장된 실제 문자 정보를 읽습니다.

스캔 PDF와 이미지는 문자 레이어가 없으므로 PaddleOCR를 사용합니다. 이미지를 전처리한 후 모델이 글자와 위치, 확신도를 반환합니다. 후처리에서는 한 단어씩 줄이 바뀌는 문제를 줄이고 다단 문서의 읽기 순서를 조정합니다.

결과의 bbox는 글자 위치를 나타냅니다. 사용자가 추출 문장을 누르면 PDF 위의 해당 위치가 강조됩니다.

### 저장과 히스토리

Supabase Storage는 파일 창고입니다. 원본 PDF와 이미지를 저장합니다. Supabase ocr_documents는 데이터 표입니다. 파일명, Storage 경로, 추출 텍스트, bbox, 상태를 저장합니다.

히스토리를 누르면 백엔드가 현재 사용자의 문서인지 확인합니다. 확인이 끝나면 OCR 결과와 원본 파일을 반환해 화면을 복원합니다.

### AI와 RAG

OCR 오른쪽에는 텍스트 보기, 구조화, 표 탭이 있습니다. 구조화와 표는 Gemma2 모델을 사용합니다. 모델이 자유로운 문장 대신 JSON 형식으로 답하게 요청하고, React는 JSON을 카드나 표로 렌더링합니다.

AI 채팅에서는 문서를 여러 청크로 나눕니다. 질문 단어와 많이 일치하는 청크 네 개를 고르고 질문과 함께 Gemma에 전달합니다. 모델은 이 문서 근거 안에서 답하도록 프롬프트를 받습니다.

이를 RAG라고 부르지만 현재 검색은 키워드 기반입니다. Embedding은 문장의 의미를 숫자 벡터로 만드는 기술입니다. Embedding과 벡터 DB를 연결하면 정확한 단어가 달라도 의미가 비슷한 근거를 찾을 수 있습니다.

### 개발자 성능 평가

개발자는 OCR 페이지 아래의 비교 텍스트 영역을 사용합니다. 왼쪽에는 OCR 전체 결과가 있고 오른쪽에는 사람이 검수한 정답인 Ground Truth를 넣습니다. 정답은 직접 입력하거나 TXT 또는 JSON으로 불러올 수 있습니다.

서버는 정답을 저장할 때 토큰을 비교합니다. OCR과 정답에 모두 있는 토큰은 TP, OCR에만 있는 토큰은 FP, 정답에만 있는 토큰은 FN입니다.

Precision은 OCR이 출력한 것 중 맞은 비율이고 Recall은 실제 정답 중 OCR이 찾은 비율입니다. F1은 두 점수를 함께 평가합니다. CER는 문자를 올바르게 만들기 위해 몇 번의 추가, 삭제, 교체가 필요한지를 나타냅니다.

평가 결과는 Supabase ocr_evaluations에 저장됩니다. 리포트 페이지는 Supabase에서 최신 데이터를 다시 읽고 평균 처리 시간과 평균 Precision, Recall, F1을 보여줍니다.

### Fine-tuning

Fine-tuning 화면에서는 질문과 이상적인 답변을 입력하고 JSONL 데이터셋을 만들 수 있습니다. 그러나 현재 애플리케이션 안에서 모델 가중치를 직접 학습하지는 않습니다. 실제 학습에는 GPU 서버, LoRA 또는 QLoRA 학습 코드, 작업 상태 관리와 모델 파일 보관이 필요합니다.

### 마무리

현재 프로젝트는 OCR 추출, 원본과 결과 저장, 히스토리 복원, Gemma 변환, 문서 채팅, 개발자 성능 평가까지 하나의 흐름으로 연결되어 있습니다.

다음 중요한 개발 단계는 Embedding 벡터 검색, 서버 기준 처리 시간 측정, 페이지별 성능 통계, 자동 테스트입니다.

코드를 볼 때는 버튼, React 함수, API, FastAPI route, service, DB 순서로 따라가면 됩니다. 한 번에 모든 코드를 이해하려 하지 않고 데이터가 이동하는 경로를 따라가는 것이 가장 좋은 공부 방법입니다.

## 3. 기능 시연 순서 스크립트

1. 로그인 화면에서 일반 사용자와 개발자 역할을 설명합니다.
2. OCR 페이지에서 파일을 선택합니다.
3. 자동 실행되지 않는 것을 보여주고 `OCR 텍스트 추출` 버튼을 누릅니다.
4. PDF 미리보기와 오른쪽 텍스트를 보여줍니다.
5. 오른쪽 문장을 눌러 bbox가 강조되는지 보여줍니다.
6. 다단 문서가 왼쪽 단부터 읽히는지 확인합니다.
7. 구조화와 표 탭에서 Gemma 결과를 보여줍니다.
8. 히스토리에서 이전 문서를 다시 엽니다.
9. 개발자 계정에서는 `비교 텍스트 보기`를 누릅니다.
10. TXT 또는 JSON Ground Truth를 불러옵니다.
11. 평가를 저장합니다.
12. 성능 리포트로 이동해 새로고침합니다.
13. 처리 시간, Precision, Recall, F1 결과를 설명합니다.
14. AI 채팅에서 문서를 추가하고 질문합니다.
15. 답변과 함께 검색 근거 청크를 보여줍니다.
16. Fine-tuning 탭에서 Q&A 샘플과 JSONL 내보내기를 보여줍니다.

## 4. 질문을 받았을 때 답변 예시

### “PDF.js와 OCR은 무엇이 다른가요?”

PDF.js는 PDF 안에 이미 저장된 문자 정보를 읽습니다. OCR은 이미지 픽셀을 보고 어떤 글자인지 추측합니다. 문자 레이어가 있는 PDF는 PDF.js가 빠르고 정확하며, 스캔 PDF는 OCR이 필요합니다.

### “bbox는 왜 필요한가요?”

추출한 문장이 원본 문서 어디에서 나왔는지 연결하기 위해 필요합니다. 검수와 오류 분석에 중요합니다.

### “Supabase bucket과 table은 같은 것인가요?”

아닙니다. bucket은 PDF와 이미지 같은 원본 파일을 보관하고, table은 파일명과 추출 텍스트 같은 구조화된 데이터를 행과 컬럼으로 저장합니다.

### “RAG와 Fine-tuning은 같은가요?”

아닙니다. RAG는 질문할 때 관련 문서를 찾아 모델에게 함께 주는 방법입니다. Fine-tuning은 많은 예시로 모델의 가중치 자체를 추가 학습하는 방법입니다.

### “왜 F1이 필요한가요?”

Precision만 높으면 정답 일부만 조심스럽게 추출해도 좋아 보일 수 있고, Recall만 높으면 틀린 내용을 많이 출력해도 좋아 보일 수 있습니다. F1은 두 값을 함께 평가합니다.

### “왜 서버가 여러 개인가요?”

화면, 업무 API, OCR 추론, LLM 추론은 필요한 라이브러리와 자원이 다릅니다. 분리하면 한 기능의 장애가 전체에 미치는 영향을 줄이고 각각 독립적으로 확장할 수 있습니다.
