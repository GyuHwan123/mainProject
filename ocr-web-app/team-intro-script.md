# PicToText 팀 공유용 설명 스크립트

안녕하세요. PicToText 저장소의 구조와 현재 구현 상태를 간단히 설명드리겠습니다.

PicToText는 PDF에서 텍스트를 추출하고, 추출한 문서를 바탕으로 AI에게 질문하며, 사용자 인증과 문서 보관까지 연결하는 웹 애플리케이션입니다. 전체 구조는 React 프론트엔드, FastAPI 백엔드, SQLAlchemy 데이터베이스 계층, Supabase 인증·스토리지, Ollama 언어 모델로 구성되어 있습니다.

먼저 프론트엔드는 `frontend/src/App.jsx`를 기준으로 보면 됩니다. 로그인, 대시보드, OCR, AI 채팅, 리포트, 마이페이지가 각각 별도 페이지로 나뉘며, 로그인 토큰이 없는 사용자는 보호된 페이지에 접근할 수 없습니다. 서버 통신은 `frontend/src/api/client.js`에서 관리하고, 저장된 JWT를 모든 API 요청에 자동으로 붙입니다.

인증은 두 가지 방식입니다. 이메일과 비밀번호로 가입하면 백엔드가 비밀번호를 해시해 사용자 DB에 저장하고, 로그인 성공 시 PicToText 전용 JWT를 발급합니다. Google이나 Apple 로그인은 Supabase OAuth 세션을 먼저 받은 뒤, 그 토큰을 백엔드에서 검증하고 다시 PicToText 전용 JWT로 교환합니다. 이 방식으로 앱 내부 인증 규칙을 한 가지 토큰 형식으로 유지합니다.

OCR 화면의 현재 동작도 정확히 구분할 필요가 있습니다. 현재는 PDF.js를 이용해 PDF 내부의 문자 레이어를 브라우저에서 추출합니다. 페이지별 미리보기, 텍스트 확인, 텍스트 파일 다운로드는 동작하지만, 이미지로 스캔한 PDF를 읽는 실제 이미지 OCR 엔진은 아직 연결되지 않았습니다. 백엔드의 OCR API 역시 지금은 샘플 결과를 반환합니다.

AI 문서 채팅은 사용자가 올린 PDF, TXT, Markdown 문서를 브라우저에서 작은 청크로 나눕니다. 질문에 포함된 단어와 가장 많이 일치하는 청크 네 개를 찾아 FastAPI로 보내고, 백엔드는 그 근거를 Ollama의 `gemma2:2b` 모델에 전달합니다. 모델 서버가 꺼져 있으면 프론트엔드가 가장 관련도 높은 원문을 대신 보여줍니다. 현재 검색은 키워드 기반이므로, 벡터 임베딩과 벡터 데이터베이스를 사용하는 완성형 RAG는 다음 개발 단계입니다.

데이터 저장 위치도 기능마다 다릅니다. 사용자 계정은 SQLite 또는 PostgreSQL에 저장됩니다. 로그인 토큰과 대시보드 최근 기록은 브라우저 localStorage에 있고, 대시보드에서 업로드한 원본 파일은 Supabase Storage의 `documents` bucket에 저장됩니다. 반면 OCR 결과와 AI 채팅 문서는 아직 React 메모리에만 있으므로 새로고침하면 사라집니다.

백엔드는 `backend/main.py`에서 시작하며, 실제 API 목록은 `backend/app/api/router.py`에서 확인할 수 있습니다. 인증 API와 Ollama 채팅 API는 실제 로직에 연결되어 있습니다. OCR 기록, 리포트, 사용자 히스토리 API는 현재 고정된 샘플 데이터를 반환하므로 화면 시연용과 실제 저장 기능을 혼동하지 않아야 합니다.

로컬 개발은 두 가지 방식으로 할 수 있습니다. 전체 환경을 확인하려면 프로젝트 루트에서 Docker Compose를 사용하면 React, FastAPI, PostgreSQL, Ollama가 함께 실행됩니다. 화면만 빠르게 수정할 때는 `frontend`에서 `npm run dev`를 실행하고, 백엔드는 `backend`에서 Uvicorn을 별도로 실행할 수 있습니다. 자세한 명령과 환경 변수는 `developer-guide.md`에 정리했습니다.

보안상 가장 중요한 규칙은 Supabase service role key와 JWT secret을 프론트엔드에 넣지 않는 것입니다. `VITE_`로 시작하는 값은 브라우저에 공개될 수 있으므로 anon key와 공개 API 주소만 사용해야 합니다. 실제 `.env` 파일도 Git에 올리지 않습니다.

새 기능을 맡은 팀원은 먼저 `App.jsx`에서 화면을 찾고, 해당 `pages` 파일에서 사용자 동작을 확인한 다음, API 호출 경로를 따라 백엔드 `routes`와 `services`를 보면 가장 빠르게 전체 흐름을 이해할 수 있습니다.

다음 우선순위는 실제 OCR 엔진 연결, OCR 결과와 문서 이력 저장, 벡터 검색 도입, 정적 리포트 화면의 실제 데이터 연결, 테스트 자동화입니다.

정리하면 현재 PicToText는 인증, PDF 문자 추출, 문서 기반 AI 질문, Supabase 파일 업로드의 핵심 사용자 흐름을 시연할 수 있는 단계입니다. 동시에 실제 이미지 OCR, 영구적인 처리 이력, 벡터 검색은 앞으로 구현해야 할 영역입니다. 이 구분을 기준으로 작업하면 각 팀원이 맡을 코드와 다음 개발 범위를 빠르게 파악할 수 있습니다.
